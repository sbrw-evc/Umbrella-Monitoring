# Важность и влияние: как определяется приоритет инцидента

Страница «Важность и влияние» (`/impact`, права `impact:view` и `impact:edit`) задаёт, как
приоритет инцидента (P1…P5) следует из важности его событий и влияния на бизнес-сервисы. Это
первый шаг реагирования на инциденты из [incident-response.md](incident-response.md): от приоритета
зависят PagerDuty (важность и порог), резервное оповещение (минимальная важность) и план
реагирования.

## Как считается приоритет

1. **Важность события** (`event_severity`) — наибольшая важность источников инцидента, которые
   ещё горят, как её дал коннектор или правило RED/USE.
2. **Влияние на бизнес.** Затронутые сервисы — активные и планируемые сервисы, на которых
   работает КЕ инцидента (прямое влияние), и сервисы, которые от них зависят по `depends_on`
   (косвенное влияние; «Глубина зависимостей», по умолчанию 3 шага, 0 — только сервисы самой
   КЕ). Циклы зависимостей не мешают: каждый сервис учитывается один раз, выведенные из
   эксплуатации не учитываются. Уровень влияния — наибольшая критичность затронутых сервисов:
   «критичное», «высокое», «среднее», «низкое» или «нет влияния», если КЕ не входит ни в один
   сервис.
   Влияние **неизвестно**, если КЕ инцидента нет в каталоге или в каталоге вообще нет
   бизнес-сервисов: тогда матрица не применяется и приоритет равен важности события (правила
   при этом работают, переменная `impact` равна `unknown`). Так установка без каталога сервисов
   ведёт себя как раньше.
3. **Матрица влияния** — таблица «важность события × уровень влияния → приоритет».
4. **Правила классификации** — по порядку, после матрицы.

Приоритет пересчитывается при каждом событии инцидента (новый источник, рост или снижение
важности, восстановление источника), при привязке КЕ к инциденту, слиянии инцидентов и после
изменения каталога или настроек (КЕ перешла в другой сервис, изменилась критичность или
зависимости сервиса, сохранена политика) — на ходу, без нового события. Сохранение страницы
пересчитывает открытые инциденты сразу.

Если приоритет вырос, инцидент уходит в PagerDuty повторно с новой важностью (как и раньше
при росте важности события); в хронологии — «Важность повышена». Если политика увела приоритет от
важности события или результат изменился, в хронологии появляется запись «Приоритет …:
событие … × влияние …, правило …» (код `priority_set`). Понижение приоритета в PagerDuty не
отправляется.

Политика выключена — приоритет равен важности события, но влияние (затронутые сервисы и
уровень) всё равно считается и показывается в карточке.

## Встроенный шаблон

Пока политику ни разу не сохраняли (в том числе на установках, обновлённых с прошлых версий),
действует встроенный шаблон: политика включена, глубина зависимостей 3, матрица ниже, одно
выключенное правило-пример. Кнопка «Вернуть шаблон» сохраняет его снова.

| Событие ↓ · влияние → | Критичное | Высокое | Среднее | Низкое | Нет влияния |
| --- | --- | --- | --- | --- | --- |
| P1 · Критический | P1 | P1 | P1 | P1 | P1 |
| P2 · Высокий | P2 | P2 | P2 | P2 | **P3** |
| P3 · Средний | **P2** | P3 | P3 | P3 | **P4** |
| P4 · Низкий | **P3** | **P3** | P4 | P4 | **P5** |
| P5 · Информационный | P5 | P5 | P5 | P5 | P5 |

Логика шаблона:

- **P1 остаётся P1 всегда**: источник уже сказал, что всё плохо, понижать его опасно.
- **P5 остаётся P5**: информационные события не будят людей, даже на критичных сервисах.
- **Критичное влияние** поднимает средние и низкие события на уровень (P3 → P2, P4 → P3): то,
  что на второстепенной системе подождёт до утра, на платёжном контуре требует реакции сразу.
  P2 до P1 не поднимается — P1 оставлен за событиями, которые источник сам считает критическими.
- **Высокое влияние** поднимает только P4 → P3.
- **Нет влияния** (КЕ не входит ни в один сервис) понижает на уровень, но не ниже P5: P2 → P3,
  P3 → P4, P4 → P5. Так шум с «бесхозных» КЕ не попадает в PagerDuty с порогом P2 и в
  резервное оповещение.

Любую клетку можно изменить; клетки, отличные от важности события, выделены рамкой.

## Правила классификации

Правило — условие на CEL и действие. Правила проверяются по порядку; сработавшее правило
меняет приоритет, следующие видят уже изменённый (`severity`). Выключенные правила пропускаются.

| Действие | Что делает |
| --- | --- |
| Задать приоритет (`set`) | приоритет становится заданным P1…P5 |
| Повысить на N (`raise`) | на N уровней выше (N от 1 до 4), не выше P1 |
| Понизить на N (`lower`) | на N уровней ниже, не ниже P5 |
| Задать уровень влияния (`impact`) | уровень влияния меняется, и матрица применяется заново к важности события; правила ниже видят новый `impact` |

«Остановиться после этого правила» — если правило сработало, правила ниже не проверяются.
Условие, которое не выполнилось с ошибкой (например, обращение к метке, которой нет), пропускается,
а в объяснении приоритета показывается ошибка. Вычисление ограничено по стоимости и по
времени, так что тяжёлое условие не остановит обработку событий.

Переменные условия:

| Переменная | Тип | Значение |
| --- | --- | --- |
| `event_severity` | строка | важность события: `critical`, `error`, `warning`, `low`, `info` (P1…P5) |
| `severity` | строка | приоритет на этот момент: после матрицы и правил выше |
| `impact` | строка | уровень влияния: `critical`, `high`, `medium`, `low`, `none`, `unknown` |
| `title` | строка | заголовок инцидента |
| `ci` | строка | имя КЕ (или имя из события, если КЕ нет в каталоге) |
| `ci_kind` | строка | тип КЕ: `device`, `vm`, `service`, `other`; пусто без КЕ |
| `signal` | строка | сигнал |
| `method` | строка | `red`, `use` или `other` |
| `labels` | map | метки событий |
| `services` | список | имена затронутых сервисов, самые критичные первыми |
| `service_criticalities` | список | их критичность в том же порядке |
| `direct_services` | список | сервисы, на которых работает сама КЕ |
| `team` | строка | команда-владелец по маршруту инцидента |

Доступны строковые функции CEL (`contains`, `startsWith`, `matches`, `lowerAscii` и др.).

Примеры:

```
# Базы данных в продуктиве — на уровень выше
'env' in labels && labels['env'] == 'prod' && title.lowerAscii().contains('database')
  → Повысить на 1

# Любое событие на КЕ платёжного сервиса — не ниже P2
'Payments' in direct_services && severity in ['warning', 'low', 'info']
  → Задать приоритет P2

# Тестовые стенды — ниже на два уровня и больше ничего не проверять
ci.startsWith('test-') || ('env' in labels && labels['env'] == 'test')
  → Понизить на 2, остановиться

# Сетевые устройства ядра считаются критичным влиянием, даже если не привязаны к сервисам
ci_kind == 'device' && ci.matches('^core-')
  → Задать уровень влияния «критичное»

# Метод RED (ошибки пользователей) на сервисах с высоким влиянием — на уровень выше
method == 'red' && impact in ['critical', 'high']
  → Повысить на 1
```

Ограничения: до 100 правил, условие до 2000 символов, название до 200, идентификатор — латинские
буквы, цифры, `.`, `-`, `_` (до 64 символов, уникальный). Условие проверяется при сохранении:
синтаксис, известные переменные, результат типа bool.

## Карточка инцидента

На вкладке «Основное» блок приоритета:

```
Приоритет P2 · Высокий ← событие P3 · Средний × влияние Критичное (Payments; зависящие: Checkout) · правило «DB on prod»
```

«Как получен» раскрывает шаги: важность события, затронутые сервисы, клетка матрицы, сработавшие
правила (и правила с ошибкой).

## Проверка

Панель «Проверка» на странице: заголовок, КЕ (как её называет событие), сигнал, важность, метод
и метки примера. Результат считается по политике, которая сейчас на странице (в том числе
несохранённой), и текущему каталогу: найденная КЕ, команда, приоритет и шаги.

## API

| Запрос | Право | Что делает |
| --- | --- | --- |
| `GET /api/impact` | `impact:view` | `policy` (действующая; шаблон, пока не сохраняли — `configured: false`), `defaults` (шаблон), `levels`, `severities`, `variables`, `actions` |
| `PUT /api/impact` | `impact:edit` | сохранить политику (тело — `policy`); ответ как у GET; ошибка `invalid_impact_policy` с причиной |
| `POST /api/impact/reset-defaults` | `impact:edit` | сохранить шаблон |
| `POST /api/impact/preview` | `impact:view` | `{"event": {"title", "ci", "signal", "severity", "method", "labels"}, "policy": …необязательно}` → `{"event_severity", "severity", "impact", "ci", "team"}` без сохранения |

Сохранение пишется в журнал аудита (`settings.impact`, `settings.impact_reset`).

Поля инцидента: `event_severity` — важность события, `severity` — приоритет, `impact` —
`level` (пусто — неизвестно), `services` (с признаком `direct`), `rule`, `steps` (коды
`event_severity`, `impact_level`, `impact_unknown`, `policy_disabled`, `matrix`, `rule_set`,
`rule_raise`, `rule_lower`, `rule_impact`, `rule_error`), `at`. У инцидентов, сохранённых до
появления приоритета, `event_severity` нет: их важность считается важностью события, и политика
применяется к ним при ближайшем пересчёте.
